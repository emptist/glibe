# Deep Diff: glib vs glibe — 2026-10-02

Two projects, one author, two AI ports. This document records every design and
implementation difference found in a line-by-line comparison of both trees.
Authority is always the user's rulings in `glib/docs/RULINGS.md` and
`glib/docs/DESIGN.md`; glibe deviates from those unless noted otherwise.

---

## 1. Design differences (structural)

### 1.1 Leaf/Branch storage: integer indices vs DataBar references

**glib** stores only three integers on a leaf:
```gleam
YinLeaf(start_idx: Int, end_idx: Int, corner_idx: Int)
```
Accessing a bar value requires a list traversal: `list.take(settled, bar_idx -
start_idx)`. This is O(n) per bar and is the root cause of the O(n²) engine
measured in Question 40.

**glibe** stores DataBar references directly:
```gleam
YinLeaf(start_bar: DataBar, end_bar: DataBar, corner_bar: DataBar)
```
Every value is O(1): `growing.start_bar.sma_tiny`. The `idx: Int` field added to
`DataBar` makes the old integer arithmetic available as `.start_bar.idx`. This is
glibe's biggest improvement over glib.

**Verdict:** glibe wins. The tradeoff (larger memory per leaf) is correct — the
alternative is a quadratic engine that cannot generate its own training corpus
(glib Question 40). The refactor was correct and should be preserved.

### 1.2 Branch field naming: `enter_idx` vs `corner_bar`

**glib** branch:
```gleam
YangBranch(start_idx, enter_idx, end_idx, exit_idx)
```
`enter_idx` = the bar where the branch is recognised / the trader enters. It is
central to the AI strategy: the AI's entire edge is entering BEFORE `enter_idx`.

**glibe** branch:
```gleam
YangBranch(start_bar, end_bar, corner_bar, exit_bar)
```
`corner_bar` is set to `current_bar` at branch birth — semantically identical to
`enter_idx` — but named `corner_bar`, which is already used for the leaf's pivot
point. The name is misleading and the comment ("pivot point — last inner
opposite leaf's start_bar") describes the branch's `start_bar` logic, not
`corner_bar`.

**Field mapping** (same values, different names):

| Concept | glib | glibe |
|---|---|---|
| Retroactive start | `start_idx` | `start_bar` |
| Recognition/entry bar | `enter_idx` | `corner_bar` |
| Branch top (trend end) | `end_idx` | `end_bar` |
| Discrimination bar | `exit_idx` | `exit_bar` |

**Verdict:** glibe's values are correct but `corner_bar` should be renamed
`enter_bar` to match glib semantics and make the AI strategy legible.

### 1.3 Growing branches: `Option` vs sentinel

**glib** (per DESIGN.md §3, UC-41):
```gleam
growing_yin_branch:  Option(YinBranch)
growing_yang_branch: Option(YangBranch)
```
Branches are optional — bar 0 cannot determine either. `None` means "not yet
recognised".

**glibe**:
```gleam
growing_yin_branch: branch.DataBranch   // always YinBranch
growing_yang_branch: branch.DataBranch  // always YangBranch
```
Initialised with a sentinel bar at `new()`. This forces `has_growing_branch`
checks throughout `update_yin_branch` / `update_yang_branch` to detect the
"not-yet-born" case. It is correct but circuitous; UC-41 rules it away.

**Verdict:** glibe should switch to `Option(DataBranch)`. The sentinel is a
workaround for the absence of `Option`.

### 1.4 Typed lists vs union lists

**glib** (per UC-42, RULINGS §1.2):
```gleam
yin_leaf_list:    List(YinLeaf)
yang_leaf_list:   List(YangLeaf)
yin_branch_list:  List(YinBranch)
yang_branch_list: List(YangBranch)
```
Each list holds its own variant. Pattern matching is exhaustive with no impossible
arms.

**glibe**:
```gleam
yin_leaf_list:    List(leaf.DataLeaf)   // can hold YangLeaf — compiler allows it
yang_leaf_list:   List(leaf.DataLeaf)
yin_branch_list:  List(branch.DataBranch)
yang_branch_list: List(branch.DataBranch)
```
The union type allows the compiler to accept a `YangLeaf` in `yin_leaf_list` with
no error. This is a type-safety gap.

**Verdict:** Fixing this requires splitting `DataLeaf` into `YinLeaf`/`YangLeaf`
as separate top-level types. That is a large structural change; log it and address
in a dedicated phase.

### 1.5 Leaf growth: threshold semantics

**glib** `grow_yin` computes `extremes` over the leaf's settled range each bar
(O(n)):
```gleam
let #(lowest, highest) = extremes(list.take(settled, bar_idx - growing.start_idx))
case working.sma_tiny >. highest { ... }
```
`highest` starts at `start_bar.sma_tiny` and is always that same value for a yin
leaf (the leaf started at a new high, subsequent bars are lower). So the threshold
is effectively fixed at the start value.

**glibe** `update_yin_leaf` uses `start_bar.sma_tiny` directly — the same value,
without the traversal:
```gleam
let threshold_crossed = current_bar.sma_tiny >. start_sma
```

The corner update in both projects tracks the running minimum:
- glib: `lowest` from `extremes` = the minimum seen so far
- glibe: `corner_sma = leaf_corner_bar(growing).sma_tiny` = updated whenever a
  new minimum arrives = same value

**Verdict:** Mathematically equivalent. glibe's approach is O(1) and correct.

### 1.6 SMA ladder: four rungs vs five

**glib** has five: `sma_tiny / sma_small / sma_medium / sma_large / sma_huge`
(window 504). `sma_huge` is the fifth rung, selectable as `sma_for_bbm`, and is
a real config value (Question 17, RULINGS §1.3).

**glibe** has four: no `sma_huge`. The fifth rung is missing.

**Verdict:** glibe must add `sma_huge` (window 504) to both `DataBar` and
`indicator_settings.TimeframeSettings`.

### 1.7 `prev_*` fields on DataBar

**glib** has none. The previous bar is `list.first(databar_list)` (ruling
2026-09-18, DESIGN §3 §6).

**glibe** still has `prev_sma_tiny`, `prev_bb_m`, `prev_k`, `prev_j`. These are
frozen second copies of `databar_list` (plan 31-08 §3 in glib's terms).

Note: glibe also abuses `prev_bb_m` to store the Bollinger sigma value
(`bollinger.gleam:58`: `prev_bb_m: sigma`). This is a bug independent of the
`prev_*` ruling — sigma is derivable and should not be stored at all (DESIGN §13:
"a thing is stored only if recomputing it costs too much or loses information the
list does not contain").

**Verdict:** Delete `prev_*` fields from DataBar. Fix the sigma storage bug.

### 1.8 `idx: Int` on DataBar

**glib** has no `idx` field. The bar's position is derived: `list.length(databar_list)`.

**glibe** added `idx: Int` to DataBar to support the O(1) leaf/branch refactor
(04-02). Without it, `leaf_start_bar(growing).idx` would not be available.

**Verdict:** This is load-bearing for glibe's O(1) design. Keep it. It is the
price of avoiding O(n) traversals. The ruling "a thing is stored only if
recomputing it costs too much" justifies it — every bar requiring a `list.length`
call IS too costly.

### 1.9 KDJ RSV window: 9 vs 7

**glib** uses `kdj_window_size: 7` (from idib `kdjPeriod = 7`,
`Types.idr:178`; RULINGS §1.6, Question 25).

**glibe** uses `window_kdj_size: 9` in `config.gleam`. No source is cited for 9;
it is not from idib, not from seib, not from ibOptions.

**Verdict:** Glibe's RSV window should be 7 to match idib. This is the authority
per RULINGS §1.6; "the textbook RSV period … is what a model writes when it has
nothing to cite" (Questions Part 3, Q25 closed).

## 2. Implementation differences

### 2.1 Bollinger subdivision

Both projects use Fibonacci (0.382 / 0.618). The formula differs slightly:

- **glib**: `between(basis, edge, t) = t·edge + (1-t)·basis`
  → `bb_u2 = 0.618·bb_u3 + 0.382·bb_m = bb_m + 0.618·spread`
- **glibe**: `bb_u2 = bb_m + spread * 0.618`

Mathematically identical. Both correct. glib's `between` helper is cleaner.

### 2.2 KDJ M line: incremental SMA vs true mean

**glib** computes M as the arithmetic mean of the last `kdj_m_period` K values:
```gleam
list.map(list.take(databar_list, settings.kdj_m_period - 1), fn(bar) { bar.k })
let m = mean_of([k, ..k_values])  // true mean of last 10 K values
```
`kdj_m_period: 10` is a config setting. RULINGS §1.6: "M = SMA(K, 10) (not SMA(J,
10) — mimo's comment is wrong)".

**glibe** uses an incremental SMA approximation, hardcoded at 10:
```gleam
let m = incremental_sma(databar.m, k, 10)  // kdj.gleam:36 — EMA-like recurrence
```
This is not the arithmetic mean — it is a weighted recurrence that approximates
the mean but never equals it exactly (especially on early bars). The period is also
hardcoded rather than read from settings.

**Verdict:** glibe's M is wrong. Fix: add `kdj_m_period: Int` to
`TimeframeSettings`, set it to 10, and compute M as the true mean of the last
`kdj_m_period` K values from `databar_list` (same pattern as the σ computation).

### 2.3 Strategy

**glib** `trading/strategy.gleam` implements idib-accurate rules:
```
Buy  = kdjCrossUp OR (priceAtLowerBand AND sma7Rising AND leafCmasRising)
Sell = kdjBearishLeft AND prev_close < prev_sma_tiny AND leafCmasFalling
```
Position-aware. Reads `DataBar` signal fields directly.

**glibe** `strategy_signal` in `timeframe.gleam:342` is a stub returning `databar`
unchanged. No logic.

**Verdict:** Port glib's `strategy.gleam` rules into glibe's `strategy_signal`.
The six boolean fields are already on glibe's `DataBar`.

### 2.4 `single_bar_test`

**glib** has a `single_bar_test` function returning a verdict type (issue 31-09
in glib's planning). The Bollinger ordering is tested in the test suite, not
asserted in the hot path.

**glibe** moved the assertions out of the hot path (round-2 fix) and the
`single_bar_test` is a no-op returning `databar`. Band ordering is tested in
`glibe_test.gleam`. Correct.

### 2.5 `sourcebar_validate`

**glib** added `sourcebar_validate` (handoff 2026-09-26): a boundary validator
that checks OHLC laws and crashes loud on a corrupt feed bar before it reaches
`databar_processing`.

**glibe** has no equivalent. A malformed source bar reaches the pipeline silently.

**Verdict:** Port `sourcebar_validate` from glib (a boundary check, not a
pre-emptive Binance check — stays minimal per the user's instruction).

### 2.6 Potential yin/yang list swap in `update_yin_branch`

In glibe's `timeframe.gleam:283`:
```gleam
branch.update_yin_branch(
  timeframe.growing_yin_branch,
  databar,
  timeframe.growing_yang_leaf,
  timeframe.yin_leaf_list,      // <-- passed as yin_leaf_list
  exit_leaf_size,
)
```

In `branch.gleam`, `update_yin_branch` uses this list to compute the new branch's
`start_bar`:
```gleam
let new_start = case list.first(yin_leaf_list) {
  Ok(l) -> leaf.leaf_corner_bar(l)
  ...
```

A `YinBranch` rides YangLeaves. Its new start should be the corner of the
most-recently-completed YANG leaf — so `yang_leaf_list` is what belongs here. The
current code uses `yin_leaf_list`, which would set the start to a yin leaf's
corner. **This is a probable bug.** Needs a test to confirm.

Symmetrically, `update_yang_branch` should use `yin_leaf_list` (not `yang_leaf_list`),
and the current call at `timeframe.gleam:289` passes `timeframe.yang_leaf_list`
— that too may be swapped.

**Verdict:** Write a test with known leaf/branch sequence to verify both branches'
`start_bar` values. Fix the list parameter if wrong.

## 3. Pros and cons

### glib

**Pros:**
- Living doctrine: DESIGN.md, RULINGS.md, QUESTIONS.md, STATE.md, NAMING.md
  with 60+ user rulings verbatim and tagged
- Phase 31 stream rewrite: clean O(1) indicator pass, no prev_* fields
- Branch type has `enter_idx` — the AI's target; semantics are clear
- Growing branches are `Option` (UC-41 compliant)
- Five SMA rungs including `sma_huge` 504
- `sourcebar_validate` boundary guard
- CI guards: `no_python.sh`, `no_banned_names.sh`, `guards.sh`
- Trading strategy implemented with idib-accurate rules
- AI strategy phase-12 design and class A/B framing documented
- 30 tests (green), covers leaves + branches

**Cons:**
- O(n²) engine (Question 40 — cannot generate training corpus at 4.8M bars)
- JS target; 25 `@external` calls that block the Erlang port (glibe's reason)
- Union `types.gleam` partially survived (`MarketType` collapse, `TradeSignal`)
- `Segment` / `Fractal` / `BranchFields` deleted only after audit
- AI strategy is a phase-12 design, not code — `strategy` stub in timeframe

### glibe

**Pros:**
- Erlang/Elixir target: no `@external` for leaf/branch/indicator logic
- O(1) leaf/branch detection via DataBar references (04-02 refactor)
- `idx: Int` on DataBar enables fast index arithmetic
- `binance/types.gleam` eliminated (04-01 refactor); types live in domain modules
- Round-2 bugs all resolved (circuit breaker, assert hot-path, test wiring, etc.)
- Test suite covers SMA × 3 cases, KDJ × 2, Bollinger ordering

**Cons:**
- No living doctrine — user rulings not recorded; each session starts from scratch
- `corner_bar` name misleads; should be `enter_bar` (glib's `enter_idx` concept)
- Growing branches not `Option` (sentinel workaround, UC-41 violation)
- `List(DataLeaf)` instead of typed `List(YinLeaf)` / `List(YangLeaf)` (UC-42 gap)
- `prev_*` fields still on DataBar (ruled away in glib 2026-09-18)
- `prev_bb_m` stores sigma — wrong field, wrong purpose
- No `sma_huge` (only 4 SMA rungs; glib has 5)
- `strategy_signal` is a stub — no trading logic
- No `sourcebar_validate` boundary guard
- Potential yin/yang list swap in branch update (§2.6)
- `inner_*` leaf CMA fields on DataBar have no computation behind them (stubs)

## 5. AI strategy — what is needed and what glib has designed

### 5.1 The mission (from RULINGS §1.6)

The AI's job is to guess BEFORE `enter_idx` (glibe: `enter_bar`) arrives. Value is:
- Lead bars: how early before the recognition point the AI can act
- Entry-price edge: `close[g_enter] − close[enter]` (entering at g_enter costs less)

A filed branch with `end_bar == enter_bar` is a failure trade — the structure
recognised it too late. The AI must learn when the structure is ABOUT to
recognise a branch, not after.

### 5.2 Class A vs Class B (from phase-12 overview)

**Class A — Yang in Yang (continuation):**
- Market is in a top-level YangBranch (uptrend)
- SMA7 making new highs, price above MAs
- KDJ cross-up from elevated levels; CMAs all rising
- Entry: pullback to sma_tiny, KDJ cross-up, price touches middle BB

**Class B — Yang in Yin (reversal):**
- Inner YangBranch forming inside a top-level YinLeaf (downtrend)
- KDJ oversold bouncing; price near lower BB
- The "trap": quick rally hits yin leaf CMA then bounces back — many fail
- Entry only after confirmation: multiple inner yang branches, CMAs starting up

### 5.3 Feature set (FractalFeatures design from phase-12)

```gleam
// Proposed — not yet in glibe
pub type FractalFeatures {
  FractalFeatures(
    // Leaf context
    leaf_progress: Float,        // bar_idx / leaf estimated size
    leaf_age: Int,               // bars since leaf started
    // CMA context
    yin_leaf_cma_slope: Float,
    yang_leaf_cma_slope: Float,
    inner_yang_cma_slope: Float,
    // Price position
    price_vs_sma_tiny: Float,    // close / sma_tiny - 1.0
    price_vs_bb_l3: Float,
    price_vs_bb_u3: Float,
    // KDJ momentum
    kdj_k: Float,
    kdj_d: Float,
    kdj_j: Float,
    kdj_cross_up: Bool,
    kdj_bearish_left: Bool,
  )
}
```

### 5.4 Why glibe cannot do AI yet

1. No `enter_bar` (currently `corner_bar` — must rename first)
2. No training corpus generator (requires O(1) engine — glibe has it after 04-02)
3. No `FractalFeatures` extraction
4. No label generation (marking branch outcomes: success/failure/enter_lead)
5. No model type (Gleam has no ML library; will need FFI to Elixir Nx or a
   pure Gleam nearest-neighbour implementation as the user forbids Python)

### 5.5 Phased AI plan for glibe

**Phase 05 — Corpus (prerequisite):**
- Fix enter_bar naming (§4.1 item 3)
- Add `sourcebar_validate` boundary
- Add replay harness: feed historical Binance bars through `sourcebar_gate` →
  `databar_processing`, collect all filed branches
- Verify against a known-good sequence (comparable to glib's corroboration test)

**Phase 06 — Feature extraction:**
- Implement `FractalFeatures` record
- `extract_features(databar, timeframe) -> FractalFeatures` for each bar

**Phase 07 — Labels:**
- For each filed branch, label: did `enter_bar` come before `end_bar`? (failure
  test); what is the `end_bar - enter_bar` lead?
- Generate a CSV/JSON dataset of (features, label) pairs

**Phase 08 — Model:**
- Analogical reasoning: find the K most similar past FractalFeatures; majority
  vote on the label. Pure Gleam, no Python (RULINGS §1.1 no Python ever).
- Alternative: Erlang NIF calling Elixir Nx — deferred; start with k-NN.

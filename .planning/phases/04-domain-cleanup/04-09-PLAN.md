## 2. 今天已查到的证据（原文 / file:line，明天直接引用，不必重查）

### 2.1 官网 `https://gleam.run/` — "Reliable and scalable"

> "Thanks to its **multi-core actor based concurrency system** that can run
> **millions of concurrent green threads**, fast immutable data structures, and a
> concurrent garbage collector that never stops the world, your service can scale
> and stay lightning fast with ease."

官网首页的并发示例**只有三行原语**，没有任何 actor / supervisor：

```gleam
let subject = process.new_subject()
// Spawn a child green thread
process.spawn(fn() { process.send(subject, "Hello, Joe!") })
echo process.receive(subject, 100)
```

### 2.2 官方 `https://gleam.run/news/gleam-v0.12-and-gleam-otp-v0.1-released/`（Louis Pilfold, 2020-10-31）

- "The core concurrency primitive in Gleam OTP is the **process**, which is a
  lightweight green thread implemented by the BEAM virtual machine … a single
  BEAM instance can happily run **millions of processes** at the same time.
  It's highly sophisticated **preemptive scheduler** will ensure they make full
  use of **all the cores of the CPU** …"
- **"there's no need for an `async/await` syntax or callbacks. Asynchronous code
  in Gleam looks exactly the same to regular synchronous code and doesn't require
  any special types such as futures or promises."** ← owner「非常简单自然」的官方出处。
- **"Erlang and Gleam don't have mutable state so locks and shared mutable state
  is not an option- instead Gleam uses channels."** / "The Gleam compiler can
  **full type check channels**." ← owner「不需要复杂补救措施」的官方出处。
- "In programs written in Erlang using OTP we tend to not use raw processes
  frequently, instead we use a higher level abstraction called `gen_server` …
  Gleam is similar, though our higher level abstraction is called **actor** and
  differs in design to `gen_server` **in order to provide type safety**."
- "Since an actor is being used here rather than a raw process **it doesn't shut
  down after running the function once** … Any of OTP's debug or system messages
  sent to the actor are automatically handled by the actor implementation, while
  they would need to be manually handled when using a raw process."
- "**Supervisors are special actors** that start other actors and then monitor
  them to ensure they are healthy." ← 监督是**容错/生命周期**，不是并行机制。

**由此得到的边界**：一次性并行任务只需要 `process.spawn` + 类型化 `Subject`；
actor 是同一个 spawn 之上「带状态的长生命周期循环 + 自动处理 OTP 系统消息」的**薄封装**，
不是并发的前提，更不是补救措施。两者都不需要锁。

### 2.4 术语上的精确化（写进结论时用，不是反驳 owner）

- 「天然多线程」：官网措辞是 multi-core **green threads / BEAM processes** +
  每核一个抢占式调度器；不是 OS 线程、不是共享内存线程。
- 「不需要 actor 那些东西」：对一次性并行任务**成立**（官方明说无需 async/await、
  future、回调）。actor 只在**需要状态跨消息存活**时才自然出现；Wisp 不用，
  Lustre 服务端用，Mist 用监督池。
- 「严格的 value、完全不住在内存里」：值**确实在内存里**（每个进程自己的堆），
  但不可变、发消息时复制、进程间**不共享**；所以没有锁、竞态、死锁。
  精确说法是「没有共享可变内存」。长生命周期状态必须住在某个进程的递归循环参数里，
  或由单一 owner 把并行结果 fold 起来 —— 这是**数据流 / 所有权**问题，不是同步补救措施。

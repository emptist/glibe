# Phase 04 Plan 07 — local wall-clock time in the web view (2026-11-09)

**Status: documentation only.** Owner ruling R30 asked for *documentation in
the corresponding modules* so the implementation can be done later. This plan
and the `////` module docs are this round's whole delivery: no conversion code,
no `tzif` dependency, no new type, no test, no `gleam.toml` change.

## The two conversions — do not merge them

| direction | boundary | owner's example | who owns the rule |
|---|---|---|---|
| market local → instant | provider / market adapter (R29) | US 09:30 open = HKT 22:30 in winter (EST) / 21:30 in summer (EDT) | IANA rule; `tzif` when a US-equity consumer exists |
| instant → viewer local | web view (R30) | one `Timestamp` renders differently in each viewer time zone | IANA rule; whichever side renders |

Both read the **same** `SourceBar.timestamp`. Neither conversion changes it,
and neither changes `interval.bucket_ends`. A market calendar rule must never
be written into a display function, and a display zone must never be mistaken
for the exchange's zone.

## What the implementation must respect

- The standard model stays `Timestamp`. No date `String`, no wall-clock-reading
  type, no local-offset field, no revival of the void `BarClock` direction
  (R27 deleted it with no compatibility layer).
- `export/csv.gleam` keeps UTC RFC3339: it is a machine-to-machine comparison
  artifact, not a human analysis view. Local formatting is a **different**
  output edge, not a change to the CSV exporter.
- A display time zone is an IANA name (`Asia/Hong_Kong`, `America/New_York`),
  never a numeric constant offset and never a hand-written DST table.
  `ibOptions/tradingtime.py:24` (`pytz.timezone('US/Eastern')`) is the
  reference shape: the rule lives in the library, not in the code.
- If the market's local time is shown beside the viewer's local time, both are
  projections of the same `Timestamp`, each labelled with its own IANA zone.
  No second time field, no second bar.
- Which side renders (BEAM HTML/JSON, or the generated `.mjs` client) and
  where the viewer zone comes from are settled when a real consumer exists
  (R26). This plan does not invent a settings type for them.

## Implementation order (R19, when the work starts)

1. `////` module doc naming **this plan** on the module that owns the display
   conversion; types first, then `///` + annotated signatures, then
   `todo as "…"` bodies. No parser, no `panic`, no catch-all over a closed set.
2. Tests first: at minimum both DST sides of one instant (winter EST vs summer
   EDT rendering of the same `Timestamp`), a viewer-zone boundary case, and a
   proof that rendering leaves the standard bar's `Timestamp` unchanged.
3. Bodies, cycling to GREEN. Introduce `tzif` 2.0.0 (+ `zones` or
   `tzif_loader`) only if the conversion lands on the BEAM side; on the
   JavaScript side use the runtime's IANA capability instead. No npm
   dependency, no hand-written `.mjs` outside `webclient/` (R16 / R18).
4. `gleam docs build` → `package-interface.json` carries this plan's link.

## What is being compared, and what is NOT

Three **minimal runnable** Erlang-target Gleam projects under
`probes/web-layer/`. They are measurement apparatus, not product packages:
the root `src/` stays pure Erlang (R15) and `webclient/` remains the product's
only JavaScript-target package (R18). All three server demos reuse that same
package for the browser half; demo (b)'s browser runtime ships inside the
`lustre` Hex package, not as project source.

| demo | server half | browser half |
|---|---|---|
| A `a_wisp` | Mist + Wisp: `/` HTML, `/bar` JSON | generated `webclient.mjs` |
| B `b_lustre` | Mist + Wisp + Lustre server component | Lustre's `priv/static` runtime |
| C `c_static` | Mist only (no framework): `/` HTML, `/bar` JSON | generated `webclient.mjs` |

"One settled bar" is the same value in all three: `SettledBar(index: Int,
close: Float)`. The path being measured is **BEAM value → HTTP response →
browser view**, not the fractal engine. The engine is not wired in here; that
is a later, separate plan. Claiming otherwise would be a fake result.

## Metrics (each one must be measured, not asserted)

1. Lines of Gleam (source, non-blank) and lines of **hand-written** JS.
2. Hex dependency count from each demo's `manifest.toml`; npm dependency count.
3. Build steps needed to produce a runnable server + browser asset.
4. One settled bar reaching the view: `curl /` and `curl /bar` output.
5. Runtime import check: `gleam build` green is NOT proof a browser asset
   resolves. Node must import the generated `.mjs`, and the server must answer
   a real request.
6. `package-interface.json` must carry this plan link on every touched module
   (R19 anti-drift check). No new sh guard.

## Docs-first / TDD order (R19)

1. This plan first. Then `////` module docs naming **this plan item**, types,
   `///` on every type/function, `todo as "…"` bodies.
2. Tests before bodies: each demo gets a gleeunit test pinning the JSON and
   HTML rendering of one settled bar. Measure RED once.
3. Fill bodies, measure GREEN: `gleam build --warnings-as-errors`,
   `gleam test`, `gleam format --check`, `gleam docs build`.
4. Start each server with a real HTTP request against it; record the output.
5. Write the conclusion and its numbers into `docs/DESIGN.md`; update
   `docs/STATE.md`, `.planning/ROADMAP.md`, and this plan's SUMMARY.

# Phase 04 Plan 12 — measure `databar_processing` as a Gleam pipeline (2026-11-12)

**Status: probe.** Owner 2026-11-12: the main body inside `databar_processing`
is `timeframe |> function1 |> function2 |> function3 ... |> functionN`, infinitely
extensible; `Timeframe` is the subject because it holds `working_databar`.
Question to answer on the compiler, not in prose: **can Gleam be written this
way? If not, which form does Gleam allow?**

**Owner's clarification, same day (verbatim)**: *"我在举例时候方便起见，没有写
function(...),所以你如果以为这是限定，那么就很难做，因为只有单参数fn才能像上面
那样写，实际上你可有有无数参数，只要第一个是所谓 subject即可，具体的看 官方文件，
搜索其中的标题包含 piplines 这部分"*. Official tour
`https://tour.gleam.run/everything/#functions-pipelines`, section **"Pipelines"**:
`rocket |> launch(1, 2)` becomes `launch(rocket, 1, 2)`; a bare right-hand
name becomes a one-argument call; a function capture can move the piped value
to a later argument. So a step is `fn(Timeframe, ...extra) -> Timeframe`: the
FIRST argument is the subject, the return value is the subject, and the other
parameters are supplied at the pipe site. `function1` is shorthand, not an
arity restriction.

R39 is the reason: one straight line; **no step passes the bar as an argument**
(the bar is the `working_databar` field). R19 is the method: `////` + `///` →
empty skeleton → unit tests → bodies → green. R35: if the shape needs a
mechanism, the definitions are wrong.

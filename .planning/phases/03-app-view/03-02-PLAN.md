<architecture_fixed_by_03_00>
- `ChartWidgetState` lives in plushie's runtime registry; the app cannot write it directly. The only legal write path is `WidgetDef.handle_event` (`widget.gleam:68-88, 290-306, 531-578`).
- A `CustomWidget` event with exact `EventTarget(window_id, id, scope: [])` hits exactly one registry entry (`widget.gleam:426-486`); a mismatch is a silent no-op. The chart widget must be a DIRECT child of the one window so its scoped ID equals `wire.chart_widget_id(...)`.
- `WidgetEvent.CustomWidget` exists at `event.gleam:230`. `EventAction.UpdateState` re-renders after state change (`widget.gleam:150-160, 544-547`).
- `bar_stream_chart` 1.2.1: `push_generating(chart, bar) -> #(Chart, GeneratedShapes)` (`src:362`) and `frame(chart, vp, mouse) -> Frame` (`src:772`) are the intended pair. `shapes/3` exists but re-wraps the whole accumulated list (`src:807`); do not use it in the hot view path. Chart opaque state holds no caller bar list (`src:199-201`).
- **No per-chart App** (re-verified 2026-11-23 from all local reviews). try_plushie's three `plushie.start` calls (`try_plushie.gleam:773-794`) ARE real Apps (new supervisor/runtime/renderer each: `plushie.gleam:191-279`), but that shape solved its two-independent-streams + big-Desk-model problem, not multi-window. Official multi-window is ONE `plushie.start` with `view -> List(window)` (`app.gleam:70-76`; `docs/RULINGS.md:5408` "All windows share the same model, update, and view"). gl-center `beam-plushie-concurrency-measured.md:274-279` says explicitly that multi-window does not need N Apps and three Apps cost 3× GPU/memory; `:392-396` says glibe's concurrency ruling and plushie multi-App shape are not yet merged. Owner `docs/RULINGS.md:5381`: try_plushie only proves plushie works; its type/business structure is not a template. Therefore glibe uses ONE App; many charts are stable-ID widgets (or, if separate OS windows are wanted, peer windows from the same App with per-window `EventTarget`), never one App per chart.
</architecture_fixed_by_03_00>
